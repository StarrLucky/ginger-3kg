# Web-приложение Meow Food + собственный слой распознавания

Статус: **Фаза 0 и Фаза 1 готовы** (обновлено 2026-09-30). Сценарий: собственный клиент параллельно с
Custom GPT — web-приложение (PWA) плюс слой распознавания еды внутри бэкенда.
Соседний документ по мультипользовательскому режиму — [MULTIUSER.md](MULTIUSER.md).

## Context

Сейчас «мозг» проекта живёт вне репозитория: Custom GPT в ChatGPT с промптом из
`food_api/gpt_prompt.md` и схемой `food_api/openapi.yaml`. Бэкенд (`food_api/api.py`, FastAPI +
SQLite на rpi.local) — чистый слой хранения и агрегации: он принимает **уже посчитанные**
`calories_kcal`/`protein_g`/`fat_total_g`/`carbs_g` (`FoodItemIn`, api.py:287) и никакой оценки
питательности не делает.

Цель — своё приложение вместо ChatGPT. Это требует двух вещей:
1. **Скопировать интеллект в новый репозиторий, remote - https://github.com/StarrLucky/ginger-3kg) ** — новый слой распознавания в бэкенде, который
   по фото/тексту возвращает готовый черновик `FoodLogIn`.
2. **Написать клиент**, который ходит в существующий REST API.

Решения, принятые по ходу обсуждения:
- **Клиент — web-приложение (PWA) в `meow_food/webapp/`, не нативный iOS.** Решающий довод:
  единственное настоящее преимущество натива — прямая запись в HealthKit — уже покрыто
  существующим мостом `/export/pending` → `/export/ack` + iOS Shortcut
  (`food_api/apple_health_shortcut.md`), который **не зависит от того, чем логируется еда**.
  Значит Apple Developer Program ($99/год), Xcode, Swift и пересборка каждые 7 дней не нужны.
  Взамен получаем: тот же Python-стек, тот же `scp`-деплой, работу на телефоне и ноуте сразу.
  Отказываемся от виджетов, Siri и надёжного оффлайна — для v1 это не нужно.
- **API-ключ LLM никогда не уходит в браузер.** Вызов модели делает бэкенд; фронтенд знает
  только сессионную куку.
- **Провайдер модели — конфиг, а не архитектура.** Бенчмарки 2026 показывают, что открытая
  Qwen3-VL-8B конкурентна на распознавании блюд (72–76%), но проваливает упакованные продукты
  (44%), а оценку массы в граммах плохо делают *все* модели. Поэтому: абстракция провайдера,
  граммовку подтверждает человек на экране правки, а выбор модели решается замером на своих фото.
- **Модель не считает БЖУ — она их не знает, она их вспоминает.** Это главное решение.
  Задача распадается на два независимых шага: *распознавание* («что на тарелке и сколько грамм»)
  и *расчёт питательности* («сколько в 180 г гречки белка»). Второй шаг — детерминированный
  лукап в справочнике, а не работа для LLM. Справочники бесплатны: **USDA FoodData Central**
  (бесплатный ключ, 1000 req/час, 140+ нутриентов на 100 г, generic-еда) и **Open Food Facts**
  (уже в репозитории, `search_products()` api.py:632, брендовое). Это убирает главный источник
  галлюцинаций и делает текстовый путь практически бесплатным.

## Целевая архитектура

```
Браузер на iPhone / ноуте  ──PWA с экрана «Домой»
  │  session cookie
  ▼
FastAPI на rpi.local  ── GET /  → StaticFiles(webapp/)
  │
  ├─ POST /recognize  ──шаг 1: РАСПОЗНАВАНИЕ (нужна LLM) ───┐
  │    │                   «что за еда + сколько грамм»      ├─ Anthropic API
  │    │                                                      ├─ Gemini API (free tier)
  │    │                                                      └─ Ollama на M4 (локально)
  │    └───────────шаг 2: ПИТАТЕЛЬНОСТЬ (LLM не нужна) ──────┐
  │                        «граммы × справочник = БЖУ»        ├─ Open Food Facts (брендовое)
  │                                                            ├─ USDA FDC     (generic)
  │                                                            └─ overrides.json (RU-специфика)
  ├─ POST /logs     (существует)
  └─ GET  /day      (существует)
```

Apple Health продолжает работать как раньше — Shortcut ходит в `/export/pending` напрямую и
про web-приложение ничего не знает.

`/recognize` **ничего не сохраняет** — возвращает черновик. Сохранение остаётся за существующим
`POST /logs`. Это намеренно: оценка порций — слабое место любой модели, поэтому экран правки
перед записью является частью дизайна, а не костылём.

Следствие разделения: **текстовый путь почти не стоит денег.** На «200 г куриной грудки и гречка»
модель делает только разбор строки в `[(куриная грудка, 200 г), (гречка, ?)]` — это сотни
токенов, посильно даже 3B-модели локально. Все числа приходят из справочников.
Vision нужен исключительно для фото.

логических изменений, чтобы дифф Фазы 1 остался читаемым.

### 0.5 CI

`.github/workflows/ci.yml` — на push и pull request, Python 3.12:

```
ruff check .  →  ruff format --check .  →  pytest
```

Без матрицы версий и без публикации покрытия: один рантайм, личный проект, лишний шум не нужен.

Локально то же самое одной командой — `Makefile` с целями `lint` / `test` / `check`.
Pre-commit-хук для линтера и тестов не ставим: на личном проекте он чаще мешает, CI поймает.
Для секретов — наоборот, см. §0.7.

### 0.7 Сканирование секретов ✅ сделано

Единственная проверка, которую **нельзя** оставлять только на CI: к моменту, когда джоба
покраснела, ключ уже в истории и его надо отзывать, а не исправлять. Поэтому две линии:

1. **Pre-commit-хук** — `scripts/hooks/pre-commit`, включается `make hooks`
   (`git config core.hooksPath scripts/hooks`, а не копия в `.git/hooks` — так хук
   версионируется вместе с репозиторием). Смотрит только staged-изменения, ~50 мс.
2. **Джоба `secrets` в CI** — та же проверка по всей истории, `fetch-depth: 0`.
   Ловит то, что закоммитили с `--no-verify` или до включения хука.

Обе вызывают один `scripts/check_secrets.sh` (`--staged` / `--history`), чтобы локально
и в CI не разъезжались правила. Скрипт делает две вещи:

- **`.env` под контролем версий** — отдельная проверка по именам файлов, до всякой регулярки.
  `.env.example`/`.sample`/`.template` разрешены.
- **`gitleaks`** (в CI пин `8.28.0`, локально `brew install gitleaks`) с `.gitleaks.toml`:
  дефолтные правила (`useDefault = true`: AWS, GitHub PAT, OpenAI, Google, приватные ключи)
  плюс своё правило на `FOOD_API_KEY`/`USDA_API_KEY`/`ANTHROPIC_API_KEY`/`GEMINI_API_KEY`.

Замеренная тонкость: своё правило сразу дало ложный позитив на `usda_api_key=usda_api_key`
(передача одноимённого аргумента в `nutrition.py`). Go RE2 не умеет lookahead, поэтому
отсекается не регуляркой правила, а `[[rules.allowlists]]` с `regexTarget = "match"`:
значение вида snake_case с подчёркиванием — это имя переменной, настоящий ключ так не выглядит.

Проверено вживую: коммит с `ANTHROPIC_API_KEY = "sk-ant-..."` и коммит с `.env` блокируются,
история репозитория чистая.

### 0.6 Чего НЕ делаем

JS в `webapp/` не линтуем. Любой линтер для фронта тянет npm и `node_modules`, а Фаза 2 прямо
построена на «без сборки, деплой тем же `scp`». Размен осознанный: сотня строк ванильного JS
не окупает тулчейн. Если фронт разрастётся — вернуться к `deno lint` (один бинарник, без
`package.json`).

## Фаза 1 — слой распознавания в бэкенде

### 1.1 `food_api/recognize_prompt.md` ✅ сделано

Извлечено из `gpt_prompt.md` секцию **«Logging food»**. Выбросить «RULE #1 — reply format»,
таблицы прогресса и suggestions — это работа UI. **Секцию «Nutrition sources» выбросить целиком**
— она становится кодом (шаг 2), а не инструкцией модели.

Задача модели сужается до: перечислить съеденное, оценить количество, классифицировать каждую
позицию как `branded` (есть бренд → искать в OFF) или `generic` (искать в USDA), дать
`lookup_query` на английском для USDA. Числа БЖУ модель **не возвращает вообще** — это отрезает
галлюцинацию на уровне схемы ответа.

### 1.2 `food_api/recognize.py` — шаг 1, распознавание ✅ сделано

```python
class Recognizer(Protocol):
    def recognize(self, text: str | None, image_b64: str | None) -> RecognizedMeal: ...
```

Схема ответа: `{items: [{name, quantity, unit, kind: branded|generic, lookup_query, brand?}],
meal_type, notes, confidence}`.

- **`AnthropicRecognizer`** — `client.messages.create(...)` с
  `output_config={"format": {"type": "json_schema", "schema": RECOGNIZE_SCHEMA}}`.
  Structured outputs гарантируют форму — парсить текст не нужно.
  `cache_control: {"type": "ephemeral"}` на системном промпте. Модель из env `RECOGNIZE_MODEL`,
  по умолчанию `claude-opus-5`.
- **`GeminiRecognizer`** — бесплатный тариф Google AI Studio, `responseSchema` для structured
  output. Квоты (март 2026): 2.5 Flash — 250 req/день, 5–10 RPM; Flash-Lite — 1000 req/день.
  **Оговорка:** на бесплатном тарифе Google использует данные для обучения. Здесь это фото еды
  и данные о здоровье — осознанный размен, поэтому провайдер не ставится дефолтом.
  Квоты уже резались в декабре 2025 — не строить на них ничего критичного.
- **`LocalRecognizer`** — POST на `LOCAL_LLM_URL` (`/v1/chat/completions`, Ollama на M4).
  Локальные модели схему держат хуже — обязательна валидация через Pydantic + один retry
  с текстом ошибки в промпте.
- Выбор через `RECOGNIZE_PROVIDER`, фолбэк на следующий при ошибке.

**Как сделано, с отступлениями от плана выше:**

- **Метод асинхронный** (`async def recognize`), а не синхронный, как в наброске Protocol.
  Иначе §1.4 не может быть `async def`: синхронный распознаватель занимал бы воркер на 5–20 с.
- **`RECOGNIZE_PROVIDER` принимает список через запятую** (`anthropic,local`). Порядок в
  строке и есть порядок фолбэка — без неявных правил вроде «остальные по алфавиту».
- **Повтор разведён с сетевыми отказами.** Отдельный `RecognizeFormatError` (не JSON / не по
  схеме / 200 с HTML вместо JSON) — только он вызывает повтор с текстом ошибки в промпте.
  Отказ транспорта повтора не получает: это был бы второй счёт за ту же недоступность.
  Развилку нашёл тест — в первой версии ретрай сторожил только валидацию, и битый JSON
  летел мимо него.
- **Повтор включён у всех провайдеров, а не только у локального.** Первая версия исходила
  из того, что Anthropic и Gemini «держат форму сами». Это верно наполовину: structured
  outputs гарантируют *набор полей*, но **не диапазоны** — `minimum`/`maximum`/`minLength`
  в них не поддержаны (проверено по документации). Значит `confidence: 95` или
  `quantity: 0` пройдут схему провайдера и упадут на Pydantic, а без ретрая это отказ
  всего запроса. `confidence` при этом просто подрезается: ронять разбор приёма пищи
  из-за косметического поля несоразмерно, позиции-то распознаны.
- **`extra: "forbid"` в Pydantic-моделях** — вторая половина защиты от галлюцинаций.
  Схема не содержит полей БЖУ, а forbid не даёт модели дописать их сбоку; тест
  `test_model_rejects_nutrition_field` это закрепляет.
- **Схема написана руками**, хотя Pydantic умеет генерировать. Причина: провайдеры
  расходятся в поддержке `$defs`/`$ref`, а нужна форма, которую примут все три.
  `test_schema_matches_model` сверяет её с моделью, так что расхождение не проедет молча.
- **Диалект Gemini — функция, а не вторая копия схемы.** `to_gemini_schema()` выкидывает
  `additionalProperties` и переводит `"type": ["string","null"]` в `nullable` — источник
  правды остаётся один.
- **Форма вызова Anthropic сверена с SDK 1.9.0**, не только с документацией:
  `OutputConfigParam` = `{effort, format}`, `JSONOutputFormatParam` = `{type, schema}`.
  План писался под `anthropic>=0.60`; актуальная ветка — 1.x, и она тянет `httpx2`
  рядом с нашим `httpx` (это нормально, разные пакеты).
- **`effort: "low"`** — задача экстрактивная, а не рассуждательная. `max_tokens=4096`
  с запасом: на Opus 5 адаптивное мышление включено по умолчанию и тоже считается в лимит.
- **Кэш промпта реально работает:** промпт ~850 токенов, минимум кэширования Opus 5 — 512.
  На моделях с минимумом 1024–4096 (Sonnet 5, Haiku 4.5) тот же breakpoint молча не сработал бы.
- **Nullable выражен через `anyOf`**, а не `"type": ["string","null"]`. В списке
  поддерживаемых structured outputs ключевых слов значится `anyOf`, а списков типов там нет —
  неверный диалект уронил бы 100% запросов к Anthropic. `to_gemini_schema()` переводит
  `anyOf` в `nullable` для Gemini.
- **Ключ Gemini уходит заголовком `x-goog-api-key`, а не в query.** httpx вшивает URL с
  параметрами в текст `HTTPStatusError`, а этот текст пишется в лог и попадает в сообщение
  «все провайдеры отказали» — ключ утекал бы при каждом 400 от Gemini.
- **Один httpx-клиент на распознаватель**, а не новый на запрос: вызов модели и так стоит
  5–20 с, добавлять к этому TLS-хэндшейк на каждый — платить за латентность дважды.
  Переданный извне клиент считается чужим и не закрывается; `aclose()` есть у всех
  провайдеров и у цепочки — §1.4 закроет их в `lifespan`.
- **Обрезка по `max_tokens` получает свой диагноз.** `MAX_TOKENS = 16000` (рекомендация для
  нестримингового вызова), и отдельная ветка на `stop_reason == "max_tokens"`: иначе
  оборванный JSON диагностировался бы как «ответ не разобрался как JSON» — правдиво,
  но уводит не туда.
- **Gemini-провайдер не проверен на живом API** — ключа нет. Форма запроса собрана по
  документации; первый же реальный вызов может потребовать правки диалекта схемы.
- **Отсутствие `ANTHROPIC_API_KEY` — предупреждение, а не отказ при сборке** (в отличие от
  `GEMINI_API_KEY`). Асимметрия намеренная: SDK умеет брать учётку и из профиля
  `ant auth login`, и жёсткая проверка сломала бы такую установку. На Pi профиля нет,
  поэтому в лог пишется предупреждение.

**Побочная находка.** `httpx` лежал только в `requirements-dev.txt`, а `nutrition.py` из §1.3
импортирует его на уровне модуля — Docker-образ не поднялся бы, как только `api.py` начнёт
импортировать `nutrition`. Перенесено в `food_api/requirements.txt` вместе с `anthropic`.

### 1.3 `food_api/nutrition.py` — шаг 2, питательность (без LLM) ✅ сделано

`resolve(items: list[RecognizedItem]) -> list[FoodItemIn]`, по источнику на каждый вид:

1. **`overrides.json`** — локальная таблица на 30–50 позиций для RU-специфики, которой в USDA
   нет или она названа иначе (сырники, творог 5%, кефир 3.2%, докторская). Проверяется первой,
   правится руками, растёт по мере использования.
2. **`kind == "branded"`** → существующая `search_products()` (api.py:632, Open Food Facts).
   Скейлинг `per_100g` на съеденные граммы через уже написанную `_off_value()` (api.py:625).
3. **`kind == "generic"`** → USDA FoodData Central. Уточнено по живому API:
   `/foods/search` отдаёт **урезанный** список нутриентов (у Foundation-записей там
   нет даже калорий), поэтому по кандидатам дозапрашивается `/food/{fdcId}` и берётся
   первый, у кого калории есть. SR Legacy опрашивается раньше Foundation — панели
   полнее. Энергия приходит дважды: 1008 в kcal и 1062 в kJ, фильтруем по единице.
4. **Единица не переводится в граммы** («2 сырника») → `needs_manual`. Средний вес
   штуки не подставляем: это было бы то же выдумывание числа.
5. **Ничего не нашлось** → вернуть позицию с `needs_manual: true` и пустыми нутриентами. UI подсвечивает её
   красным и требует ручного ввода. Лучше честная дырка, чем выдуманное число.

Результат всегда снабжается `source_ref` (`"USDA 170287"` / `"OFF Ehrmann High Protein"` /
`"override"` / `"manual"`), который показывается в UI — видно, откуда взялась каждая цифра.

**Кэш:** таблица `nutrition_cache(source, query, per_100g_json, source_ref, fetched_at)`
в той же SQLite. Гречка ищется один раз в жизни, лимит USDA (1000 req/час) перестаёт
быть темой.

**Известная слабость (замерено на живом API).** Совпадение по первому результату
посредственное: «гречка» → *Buckwheat flour, whole-groat* (мука вместо крупы),
«куриная грудка» → *breast, meat and skin* (с кожей, 172 против ~110 ккал/100 г).
Числа берутся из справочника корректно — промахивается сопоставление. Смягчено тем,
что `source_ref` виден на экране правки. Кандидат на улучшение: возвращать 2–3
альтернативы и давать выбор в UI (см. §2.4).

**Ключ USDA — заголовком `X-Api-Key`, не query-параметром** (исправлено после §1.4).
httpx вшивает полный URL в текст `HTTPStatusError`, а этот текст идёт в лог и в
`source_ref` («справочник недоступен»), — ключ в параметрах утекал бы туда при первом
же сбое USDA. Тот же класс дефекта, что нашло ревью §1.2 у Gemini. Что api.data.gov
принимает заголовок, проверено запросом с DEMO_KEY: с заголовком 200, без
аутентификации 403.

### 1.3+ Что нашёл первый живой прогон (2026-10-01)

До этого дня ни `recognize.py`, ни справочники не говорили с настоящими сервисами: тесты
работали на `MockTransport`. Первый прогон с ключом Gemini нашёл четыре дефекта, каждый из
которых мок принципиально поймать не мог.

- **Модель Gemini по умолчанию не существовала для нового ключа.** `gemini-2.5-flash` и
  `-lite` отвечают `404 «no longer available to new users»`. То есть дефолт не работал вовсе,
  а тесты этого не видели — они не ходят в сеть. Дефолт теперь `gemini-3.5-flash` (проверен
  живым вызовом). Более новая `gemini-3.8-flash` в тот момент стабильно отдавала
  `503 high demand`, 3 из 3, поэтому дефолтом не стала.
- **Брендовое искалось по русскому названию.** Для `kind="branded"` запрос в OFF строился из
  `brand + name`, где `name` — на языке пользователя, а подготовленный промптом английский
  `lookup_query` выбрасывался. «Ehrmann протеиновый пудинг» не находит ничего,
  «Ehrmann High Protein Pudding» находит товар. Тесты не ловили: мок отдавал продукт на любой
  запрос, содержимое строки никто не проверял. Теперь проверяет.
- **Open Food Facts нестабилен.** Замерено: от одного до двух `503` на четыре запроса подряд.
  Любой из них ронял позицию в `needs_manual` с нулями, хотя следующая попытка обычно
  проходит. Добавлен повтор на 5xx, 429 и обрывы связи — 4xx не повторяется, это наш запрос.
- **Пустой `USDA_API_KEY` выглядел как сетевая проблема.** USDA отвечает `403 API_KEY_MISSING`,
  позиция уходила в manual с текстом «справочник недоступен» — он отправляет искать неполадки
  в сети, хотя дело в незаполненном окружении. Теперь проверяется до запроса и называется прямо.

**Известная слабость §1.3 подтвердилась, и она хуже, чем описывал план.** На живом USDA
(с `DEMO_KEY`):

| Запрос | Что нашлось | Ккал на порцию |
|---|---|---|
| отварная гречка | Buckwheat groats, roasted, cooked | 166 — верно |
| куриная грудка | Chicken, broilers, breast | 236 — правдоподобно |
| овсянка на воде | **Pasta, fresh-refrigerated** | 328 — не та еда |
| кофе с молоком | **Candies, milk chocolate coated** | **1098** — ошибка в 20 раз |

Две позиции из четырёх — другая еда, и «кофе с молоком» в 1098 ккал тихо испортит дневной
учёт. Это не ошибка арифметики: числа из справочника берутся верно, промахивается
сопоставление. Смягчено тем, что `source_ref` виден на экране правки, но полагаться на то,
что человек каждый раз заметит, нельзя. **Нужно решать отдельно** — кандидат из §2.4 (отдавать
2–3 варианта и давать выбор) выглядит обязательным, а не желательным.

### 1.3++ Разворот: числа даёт модель, кэш по `lookup_query` (2026-10-01)

**Решение §1.3 отменено после замера.** Оно гласило: «модель называет еду, числа БЖУ берутся
из справочника — это отрезает главный источник галлюцинаций». Защита от выдуманных чисел
сработала, но на освободившееся место пришла ошибка сопоставления, и она оказалась крупнее
той, от которой уходили.

**Что намерено.** На тех же блюдах: модель права во всех четырёх случаях, справочник — в двух.

| Блюдо | Модель | USDA | Разумное значение |
|---|---|---|---|
| кофе с молоком 200 мл | 45 | **1098** — *Candies, milk chocolate coated* | ~40–60 |
| овсянка на воде 250 г | 150 | **328** — *Pasta, fresh-refrigerated* | ~180 |
| гречка отварная 180 г | 198 | 166 — *Buckwheat groats, cooked* | ~166 |
| куриная грудка 150 г | 248 | 236 — *Chicken, breast* | ~248 |

**Цена замерена, не оценена.** Два одинаковых прогона, отличавшихся только требованием вернуть
БЖУ: 31 078 против 31 335 токенов, то есть **+257 на две позиции, ~130 на позицию**. По
тарифам на 2026-10-01 это 0,64 ¢ за приём пищи на Opus 5, 0,26 ¢ на Sonnet 5, 0,13 ¢ на
Haiku 4.5 и ноль на free tier Gemini — порядка $0–9 в год. Экономить на этом нечего.

**Что сделано.**

- Модель возвращает `per_100g` со всеми девятью колонками. **На 100 г, не на порцию:** это
  свойство еды, его можно кэшировать и масштабировать существующей арифметикой. Сумма на
  порцию не переиспользуется для другого веса и заставляла бы модель умножать — а в умножении
  ошибаются чаще, чем в самих значениях.
- Новый порядок источников: `overrides.json` → **кэш по английскому `lookup_query`** →
  Open Food Facts (только брендовое) → числа модели → `needs_manual`.
- **Кэш решает воспроизводимость.** Без него модель могла бы сегодня сказать 126, завтра 131,
  и сравнение дней стало бы шумным. По ключу `lookup_query` еда считается один раз в жизни,
  повторы бесплатны и идентичны, а поправить число можно один раз в `overrides.json`.
- Источник кэша теперь один (`food`), а не два (`usda`/`off`): одна и та же еда не должна
  считаться заново из-за того, что в прошлый раз её сочли брендовой.
- **Брендовое по-прежнему идёт в OFF первым** — там числа с этикетки конкретного продукта,
  чего модель знать не может (проверено: Ehrmann High Protein, 148 ккал на порцию). Отказ OFF
  больше не теряет позицию: подставляется оценка модели.
- **USDA убран из рабочего пути.** `usda_lookup()` и её тесты оставлены намеренно: в них
  накоплено знание о квирках API (энергия в kJ под другим id, неполные карточки Foundation,
  порядок SR Legacy), и Фаза 3 будет мерить её против модели как базовую линию.
  `USDA_API_KEY` рабочему пути больше не нужен, параметр `usda_api_key` из `resolve()` убран —
  мёртвый параметр врал бы, будто справочник всё ещё опрашивается.

**Чего это стоило в защите.** Выдуманное число снова может попасть в учёт — ровно то, от чего
§1.3 уходил. Защищаемся иначе: `source_ref` говорит `model: <запрос>`, видно на экране правки;
число кэшируется, поэтому ошибка не плавает, а повторяется и потому заметна; `overrides.json`
правит её навсегда одной строкой.

Тесты: 199. Новый порядок проверен мутациями — отключали кэш, подменяли ключ кэша на название,
отбирали у OFF приоритет для брендового, убирали фолбэк на модель при отказе OFF, пропускали
отрицательные макросы.

### 1.4 Новый эндпоинт в `api.py` ✅ сделано

`POST /recognize` (с `dependencies=[Depends(_check_key)]`, рядом с `/logs`):
приём `{text?: str, image_b64?: str, meal_type?: str, consumed_at?: str}` →
`recognize()` → `resolve()` → возврат черновика `FoodLogIn` + `source_ref`/`needs_manual`/`notes`.
Хендлер **`async def`** с `httpx.AsyncClient`, не синхронный `def`: вызов модели долгий (5–20 с),
иначе он занимает воркер из общего пула — ровно та проблема, что `MULTIUSER.md` §1 отмечает
для 15-секундного `/products`. Лукапы в USDA/OFF пускать через `asyncio.gather`.

**Как сделано, с отступлениями от плана.**

*Найдено по дороге, план этого не предвидел:*

- **`nutrition_cache` не была заведена в схеме.** `CREATE_CACHE_TABLE` существовала в
  `nutrition.py` с §1.3, но `_SCHEMA` в `api.py` её не содержала — таблицу создавала только
  тестовая фикстура. Первый же лукап на живой базе упал бы на `no such table`. Добавлено в
  `_SCHEMA`; `_init_schema` идемпотентна, миграция не нужна.
- **Dockerfile копировал только `api.py`.** После того как `api.py` начал импортировать
  `nutrition` и `recognize` на уровне модуля, образ переставал подниматься вообще —
  `ModuleNotFoundError` на старте, включая `/logs` и `/day`, которыми пользуется Custom GPT.
  Теперь копируются `api.py nutrition.py recognize.py recognize_prompt.md overrides.json`.
  Проверено не сборкой (демон не поднят), а импортом `api` из каталога с ровно этим набором
  файлов — замыкание по импортам сходится.
- **`resolve()` был последовательным.** §1.3 сознательно выбрал последовательность
  («кэш делает повторы бесплатными»), но это рассуждение про повторы *между* запросами, а
  внутри одного приёма пищи позиции разные. Переведён на `asyncio.gather`, как и требует план.
  Две одинаковые позиции в одном приёме сходят в сеть дважды — допущено сознательно:
  `cache_put` идемпотентен, а реестр запросов в полёте дороже, чем этот случай стоит.

*Решения, которых в плане не было:*

- **Распознаватель строится лениво, при первом обращении, а не в `lifespan`.** Ошибка в
  `RECOGNIZE_PROVIDER` не должна ронять приложение целиком: в эту же базу через `/logs` и
  `/day` ходит Custom GPT, которому распознавание не нужно. Кривая конфигурация даёт 503 на
  одном эндпоинте, а не недоступность сервиса. Есть тест, который проверяет ровно это.
- **`httpx.AsyncClient` под лукапы — один на приложение**, в `lifespan`, с таймаутом 30 с.
  Закрывается там же вместе с распознавателем (`aclose()`), иначе asyncio ругается на
  брошенные соединения при остановке.
- **Коды ответов.** Отказ модели — `502`, а не `500`: отказал апстрим, клиенту стоит повторить.
  Картинка сверх лимита — `413` на границе API, до оплаченного вызова модели.
  Ненастроенный провайдер — `503`.
- **`meal_type` от пользователя перекрывает догадку модели**, а не наоборот.
- **Соединение с SQLite живёт через `await`'ы лукапов.** Запросы к нему короткие и локальные
  (кэш), event loop они держат на микросекунды — на это пошли сознательно, чтобы не городить
  пул на одного пользователя.

**Контракт ответа.** `draft` отдаётся ровно в той форме, которую принимает `POST /logs`:
списки нутриентов `NUTRIENT_KEYS` и `NUTRIENTS` совпадают поле в поле. Это закреплено тестом
`test_draft_is_accepted_by_logs_unchanged` — он берёт ответ `/recognize` и постит его в `/logs`
без единой правки. Если контракт разойдётся, тест это поймает.

Тесты: 19 новых (18 на эндпоинт + 1 на параллельность `resolve`), всего 138. Каждый
нетривиальный проверен мутацией — правка ломалась намеренно, тест обязан был упасть.

### 2.1 Отдача статики из FastAPI ✅ сделано

```python
app.mount("/app", StaticFiles(directory="webapp", html=True), name="webapp")
```
В Dockerfile добавить `COPY webapp/ /app/webapp/` — сейчас копируется только `api.py`.

**Как сделано, с отступлениями от плана.**

- **Каталог — `food_api/webapp/`, а не `meow_food/webapp/`.** Контекст сборки Docker — это
  `food_api/`, поэтому `COPY webapp/` работает только оттуда.
- **Путь в `StaticFiles` абсолютный** (`Path(__file__).parent / "webapp"`), а не строка
  `"webapp"`: рабочий каталог различается у uvicorn в контейнере, у локального запуска и у
  pytest из корня репозитория, а `StaticFiles` проверяет существование каталога в момент
  монтирования и уронил бы импорт `api` целиком.
- **Монтирование в самом конце `api.py`**, после всех эндпоинтов. Тест
  `test_api_still_wins_over_static` фиксирует, что `/day` и `/health` статикой не перекрыты.
- **`API_BASE` во фронтенде вычисляется**, а не зашит: приложение живёт на `/app/`, а через
  туннель — на `/food/app/`. `new URL('..', document.baseURI)` даёт верную базу в обоих случаях.

**Целостность оболочки проверяется тестами, потому что сборки нет.** Ломаться будут не типы, а
пути: ссылка в `index.html` или запись в списке кэша `sw.js` переживут переименование файла
молча. Отдельно стоит `test_service_worker_caches_only_existing_files` — `cache.addAll`
отвергает **весь** список, если хоть один путь даёт 404, и делает это тихо: приложение
продолжает работать, просто перестаёт открываться офлайн.

**Иконки генерируются скриптом** `scripts/make_icons.py` — PNG пишется руками через
`zlib` + `struct`. Тащить Pillow ради трёх квадратов несоразмерно, а бинарники без способа их
перегенерировать — плохой вклад в репозиторий. Тест сверяет сигнатуру PNG и заявленный размер.

Проверено живым прогоном через настоящий HTTP, а не только TestClient: оболочка отдаётся без
авторизации, `/day` без ключа — 401, вход ставит куку, по куке без заголовка — 200, после
выхода — снова 401.

### 2.2 Авторизация: кука вместо ключа в JS ✅ сделано

Сейчас `_check_key` (api.py:142) читает только заголовок `X-API-Key`. Расширить до
«заголовок **или** кука `session`» — обратная совместимость с Shortcut и garmin-sync сохраняется
полностью. Плюс `POST /auth/login` (принимает `FOOD_API_KEY`, ставит `HttpOnly`, `Secure`,
`SameSite=Lax` куку на год) и `POST /auth/logout`.

Почему не хранить ключ в `localStorage`: Safari чистит script-writable storage при простое,
и ключ будет периодически теряться. Плюс `HttpOnly`-кука недоступна из JS — при XSS её не украсть.

**Как сделано, с отступлениями от плана.**

- **В куке лежит случайный токен, а не сам `FOOD_API_KEY`.** План этого не уточнял, а разница
  практическая: утёкшую куку можно отозвать через `/auth/logout`, не трогая ключ, которым ходят
  Shortcut и garmin-sync. Положи мы в куку ключ — отзыв означал бы ротацию ключа и поломку обоих
  заодно. Цена — таблица `sessions(token, created_at)` и один индексированный SELECT по PK на
  запрос с кукой. Тест `test_logout_revokes_only_its_own_session` фиксирует главное следствие:
  выход на телефоне не выкидывает из сессии на ноутбуке.
- **Добавлен `GET /auth/status`** — фронтенду нужно знать, показывать ли экран входа, не дёргая
  для этого `/day`.
- **Сравнение ключа переведено на `secrets.compare_digest`.** Прежнее `!=` выходит на первом
  различающемся байте. Пока ключ жил только в заголовке от Shortcut, это было теоретизированием;
  с кукой поверхность стала браузерной.
- **Отсутствие учётных данных теперь 401, а было 422.** 422 был артефактом обязательного
  `Header(...)`: FastAPI отвергал запрос как невалидный до проверки ключа. Заголовок стал
  опциональным (есть альтернатива — кука), и отсутствие учётных данных — это ровно 401.
  Характеризационный тест обновлён с объяснением; Shortcut и garmin-sync заголовок всегда шлют,
  их это не касается.
- **`COOKIE_SECURE`** в окружении: по умолчанию 1, выключается только для локальной отладки по
  http, где браузер Secure-куку не сохранит.

Тесты: 13, каждый проверен мутацией — куку подменяли на сам ключ, `logout` на удаление чужих
сессий, проверку токена в базе убирали совсем, `HttpOnly` снимали, неверный заголовок откатывали
к куке. Все пять пойманы.

### 2.3 Камера и сжатие ✅ сделано

```html
<input type="file" accept="image/*" capture="environment">
```
На iOS открывает камеру сразу. Дальше в JS: `createImageBitmap` → `<canvas>` → long edge 1024 px
→ `toBlob('image/jpeg', 0.7)` (≈150 КБ) → base64. Сжатие **обязательно на клиенте**: держит
изображение около ~1100 токенов и не грузит канал Pi.

### 2.4 Экран правки — центральный, а не подтверждение ✅ сделано

Название, граммовка и БЖУ каждой позиции правятся руками; граммы — главное поле, потому что это
слабое место любой модели. Под каждой позицией — `source_ref` («USDA 170287», «OFF: Ehrmann High
Protein»), видно происхождение цифр. Позиции с `needs_manual: true` подсвечены и блокируют
сохранение, пока не заполнены.

### 2.5 Мелочи, которые решают ощущение «это приложение» ✅ сделано

- `<meta name="apple-mobile-web-app-capable" content="yes">` + `apple-touch-icon` → запуск с
  экрана «Домой» без адресной строки. На iPhone это WebClip, а не полноценная PWA — service
  worker урезан, Background Sync нет. Для сетевого по своей природе приложения это неважно.
- Таймаут на `/recognize` 60 с + явный индикатор: Pi + туннель + модель дают 5–20 с.
- Оптимистичный UI при сохранении: `POST /logs` возвращает готовый `day` (api.py:353) —
  перерисовываем экран дня прямо из ответа, без второго запроса.
- `progress` / `remaining_with_activity` рендерятся как есть: весь расчёт уже в `_day_summary`
  (api.py:255–273), дублировать на JS нечего.
- Данные живут на сервере, поэтому вычистка браузерного хранилища ничего не ломает.

**Как сделано, с отступлениями от плана (§2.3–2.5).**

- **Файлы разбиты мельче, чем в таблице выше:** `app.js` (состояние и обработчики),
  `render.js` (разметка), `photo.js` (сжатие), `api.js` (обёртки). Логика и построение DOM в
  одном файле читаются плохо в обе стороны.
- **`needs_manual` блокирует сохранение не «пока стоит флаг», а пока не вписаны калории.**
  Первая версия текста обещала «сними отметку, нажав на строку источника» — взаимодействия,
  которого не существовало. Вместо того чтобы делать отдельный жест, отметка снимается сама,
  когда в позицию вписали число: обещание стало правдой, а подсветка перестала быть
  украшением, которое научаешься игнорировать.
- **Перебор цели показан цветом, а не обрезан.** Полоса упирается в 100%, но заливка краснеет.
  Молча обрезать число значило бы скрыть ровно тот факт, ради которого на экран и смотрят.
- **Всё пользовательское вставляется через `textContent`, не `innerHTML`.** Названия еды
  приходят от модели, то есть в конечном счёте от того, что пользователь сфотографировал.

**Чего тесты не покрывают, и это надо знать.** Проверено: все файлы отдаются, модульные
импорты разрешаются, каждый `getElementById` находит свой id в разметке, поля экрана правки
совпадают со схемой `POST /logs`, список кэша в `sw.js` не содержит несуществующих путей.
**Не проверено:** поведение в настоящем браузере — вёрстка, камера, `createImageBitmap`,
регистрация service worker. Браузера в окружении сборки нет; это остаётся на первый запуск
на телефоне.

### 2.7 Разбор ревью Фазы 2

Десять находок, все приняты. Четыре были поведением JS, которое тогда не покрывалось ничем —
тесты проверяли только целостность путей. Это и стало главным выводом: появился стенд
`food_api/webapp/tests/run.mjs` на Node с заглушкой DOM, подключённый к `make check`.

**Правки, менявшие поведение:**

- **Экран дня оставался без чисел.** `if (day.progress)` считал заданными цели, которых нет:
  `_day_summary` кладёт `progress` при любой строке в `targets`, но наполняет его только по
  заданным ключам, и цель по одному лишь `weight_kg` давала `progress: {}` — пустой объект,
  в JS истинный. Проверено на живом сервере. Итоги теперь показываются **всегда**, полосы
  прогресса — дополнением к ним, а не вместо: при цели по одному макросу остальные цифры
  раньше пропадали с экрана.
- **Очистка поля макроса делала черновик несохраняемым.** В позицию писалась `''`, валидация
  её не ловила, `POST /logs` отвечал 422 на обязательном float — и пользователю нечем было
  понять, какое поле виновато. Пустое поле теперь ноль, плюс проверка всех четырёх макросов
  в `draftProblem`.
- **Ошибки 422 показывались как `[object Object]`.** FastAPI отдаёт `detail` строкой у
  `HTTPException` и **списком объектов** у ошибки валидации. Добавлен разбор обеих форм.
- **Потеря сессии оставляла мёртвый экран.** После старта 401 нигде не обрабатывался:
  пользователь видел текст ошибки на рабочем экране и не имел формы входа. Обработчик
  теперь один на весь модуль API; `/auth/*` из него исключены — там 401 штатный ответ.
- **Обновление не доехало бы до телефона никогда.** Service worker работал cache-first, а
  `VERSION` зашита в исходник и ничем не поднимается. Браузер переустанавливает воркер только
  при изменении самого `sw.js`, так что выкаченное исправление не увидело бы устройство,
  которому оно нужнее всего. Переведён на stale-while-revalidate.

**Укрепление авторизации:**

- Сессии истекают **на сервере**, а не только через `max-age` куки: `max-age` — просьба к
  браузеру, а не ограничение, и снятый с устройства токен жил бы вечно. Просроченные строки
  чистятся при входе — база общая с food-api из `meow_food`, расти таблице незачем.
- `/auth/login` ограничен: пять неудач с адреса — и пять минут отказа. Вход теперь достижим
  из любого браузера через туннель, а вся защита держится на энтропии `FOOD_API_KEY`;
  `compare_digest` закрывает канал по времени, но не подбор. Блокировка проверяется **до**
  сравнения ключа — иначе она обходится верной попыткой.
- `SESSION_COOKIE` читается через `Cookie(None, alias=...)`. Была нагружена только на запись,
  и переименование давало бы молча мёртвые сессии при каждом входе.

**Мёртвый код убран:** `deleteLog` экспортировался, `renderMeal` проставлял `data-log-id`, но
жеста удаления не было. Дыра закрыта отдельной правкой — см. §2.8.

**Чего по-прежнему нет.** Стенд на Node заменяет DOM заглушкой и проверяет логику разметки,
разбор ошибок и реакцию на 401. Вёрстка, камера, `createImageBitmap` и регистрация service
worker так не проверяются и проверены здесь быть не могут. Переход на
stale-while-revalidate тоже проверен только чтением: окружения service worker в тестах нет.

### 2.8 Удаление записи из webapp ✅ сделано

Закрывает дыру, оставленную разбором ревью: ошибочно распознанный приём пищи убирался только
через Custom GPT или curl.

**Почему это не кнопка у строки.** `DELETE /logs/{id}` удаляет запись целиком, а экран дня
показывает *позиции*. Один приём пищи вполне может состоять из нескольких записей — обед
записали, потом дописали яблоко. Кнопка у позиции унесла бы соседние: показанное не совпадало
бы с удаляемым. Поэтому позиции группируются по `log_id`, и удаление стоит у группы.

**Подтверждение в два шага, а не `confirm()`.** Системный диалог в приложении, запущенном с
экрана «Домой», показывает домен и выглядит чужеродно. Вместо него кнопка «Убрать»
разворачивается в «Отмена» / «Да» с текстом, который прямо говорит, сколько позиций уйдёт.

**404 трактуется как «уже убрали с другого устройства»** — день перерисовывается, а не
показывается ошибка про то, чего и так нет. Экран рисуется из ответа `DELETE`, который уже
содержит пересчитанный день: второй запрос не нужен.

Проверено живым сервером на том самом случае, ради которого всё затевалось: обед из двух
записей, удалена одна — вторая с двумя позициями цела, ужин не тронут, повторное удаление
даёт 404. Тесты: 5 в стенде на Node и 2 на стороне API, все проверены мутацией (сняли
группировку, удалили без подтверждения, подставили чужой `log_id`, сломали отмену).

### 2.6 Доступ снаружи ✅ решено, деплой за владельцем

ngrok на бесплатном тарифе показывает **заглушку перед HTML-трафиком** — API с заголовками её
не видит, а браузер, открывающий страницу, упрётся. Клик «Visit» ставит cookie на 7 дней, так
что жить можно, но для запуска с экрана «Домой» это ломает ощущение приложения.

**Рекомендация: Cloudflare Tunnel** — бесплатно, без заглушки, свой домен, без лимитов трафика.
Это ровно пункт из `MULTIUSER.md` §5 (Phase 2), просто делается раньше. Альтернатива на первое
время — оставить ngrok и мириться с еженедельным тапом.

**Статус: готово со стороны кода, ждёт аккаунта.** Туннель поднимается ключом Cloudflare,
которого у меня нет, поэтому здесь — разбор и готовая конфигурация, а не сделанный деплой.

**Приложение работает по обоим маршрутам, и это проверено.** База API вычисляется от
расположения страницы (`new URL('..', document.baseURI)`), а не зашита:

| Маршрут | Страница | База API |
|---|---|---|
| Свой поддомен через Cloudflare | `https://food.<домен>/app/` | `https://food.<домен>/` |
| Существующий роутер с префиксом | `https://<домен>/food/app/` | `https://<домен>/food/` |

Тесты `за туннелем с префиксом база сохраняет префикс` и `запросы уходят по вычисленной базе`
закрывают второй случай; зашитый корень они ловят. **Условие для префиксного маршрута:**
роутер обязан префикс *срезать* (в Caddy — `handle_path /food/*`, не `handle`), иначе запросы
придут как `/food/day`, а маршрут в FastAPI — `/day`.

**Что нужно сделать руками** (аккаунт Cloudflare, домен в нём):

1. В Zero Trust → Networks → Tunnels создать туннель, скопировать токен.
2. Добавить public hostname: `food.<домен>` → `http://food-api:8000`.
3. Положить токен в `.env` как `CLOUDFLARE_TUNNEL_TOKEN` (он секрет — в git не коммитить,
   `.gitleaks.toml` про него не знает, потому что в репозитории его быть не должно).
4. Добавить сервис в `docker-compose.yml`:

```yaml
  cloudflared:
    image: cloudflare/cloudflared:latest
    container_name: food-tunnel
    restart: unless-stopped
    command: tunnel --no-autoupdate run
    environment:
      - TUNNEL_TOKEN=${CLOUDFLARE_TUNNEL_TOKEN}
    depends_on:
      - food-api
    networks:
      - default
```

5. В `.env` выставить `TRUST_CLIENT_IP_HEADER=CF-Connecting-IP` — см. ниже, это не косметика.
6. `COOKIE_SECURE` оставить `1`: Cloudflare даёт https, и Secure-кука доедет.

**Счётчик попыток входа за прокси — следствие §2.6, которое чуть не осталось незамеченным.**
`request.client.host` за туннелем — адрес прокси, а не клиента, и все складываются в одно
ведро: перебор с чужой машины заблокировал бы вход владельцу. Заголовок с настоящим адресом
теперь берётся, но **только если назван явно** в `TRUST_CLIENT_IP_HEADER`. Доверять ему по
умолчанию было бы хуже, чем не доверять вовсе: заголовок подставляет сам клиент, и счётчик
обходится сменой значения на каждой попытке. Из `X-Forwarded-For` берётся крайний слева —
это клиент; крайний справа был бы общим прокси, и клиенты снова слились бы в один.

**Чего это не решает.** ngrok остаётся в `~/diary_api` для Custom GPT — его трафик идёт с
заголовками и заглушки не видит, так что менять там нечего. Cloudflare нужен ровно ради
браузера.

## Фаза 3 — выбор модели по замеру, а не по ощущениям

`food_api/eval/run_eval.py` + `food_api/eval/photos/` + `ground_truth.json`.

1. Снять ~20 фото типичных для тебя блюд, взвесив порции (это единственный способ получить
   честный ground truth по граммам).
2. Прогнать каждое фото через все настроенные провайдеры.
3. Вывести таблицу: MAE по ккал, MAE по белку, доля верно названных блюд, время ответа,

Кандидаты: `claude-opus-5`, `claude-sonnet-5`, `claude-haiku-4-5`, `gemini-2.5-flash` (free tier),
локальная `qwen3-vl:8b` через Ollama на M4 (`brew install ollama`, ~6 ГБ в 4-битном кванте).

угадала ли граммовку. БЖУ приходят из справочника и от модели не зависят, поэтому разброс между
провайдерами должен резко сократиться по сравнению с «всё делает LLM». Если так и выйдет —
можно смело брать самый дешёвый или локальный вариант.

Локальный вариант бесплатен, но требует, чтобы Mac был включён и доступен с Pi
(проще всего — Tailscale между ними). Практичная конфигурация: `local` как дефолт,
автоматический фолбэк на Anthropic при недоступности.
