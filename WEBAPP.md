# Web-приложение Meow Food + собственный слой распознавания

Статус: **Фаза 0 готова, Фаза 1 частично** (обновлено 2026-09-19). Сценарий: собственный клиент параллельно с
Custom GPT — web-приложение (PWA) плюс слой распознавания еды внутри бэкенда.
Соседний документ по мультипользовательскому режиму — [MULTIUSER.md](MULTIUSER.md).

## Context

Сейчас «мозг» проекта живёт вне репозитория: Custom GPT в ChatGPT с промптом из
`food_api/gpt_prompt.md` и схемой `food_api/openapi.yaml`. Бэкенд (`food_api/api.py`, FastAPI +
SQLite на rpi.local) — чистый слой хранения и агрегации: он принимает **уже посчитанные**
`calories_kcal`/`protein_g`/`fat_total_g`/`carbs_g` (`FoodItemIn`, api.py:287) и никакой оценки
питательности не делает.

Цель — своё приложение вместо ChatGPT. Это требует двух вещей:
1. **Скопировать интеллект в новый репозиторий, remote - https://github.com/StarrLucky/ginger-3kg) ** — новый слой распознавания в бэкенде, который
   по фото/тексту возвращает готовый черновик `FoodLogIn`.
2. **Написать клиент**, который ходит в существующий REST API.

Решения, принятые по ходу обсуждения:
- **Клиент — web-приложение (PWA) в `meow_food/webapp/`, не нативный iOS.** Решающий довод:
  единственное настоящее преимущество натива — прямая запись в HealthKit — уже покрыто
  существующим мостом `/export/pending` → `/export/ack` + iOS Shortcut
  (`food_api/apple_health_shortcut.md`), который **не зависит от того, чем логируется еда**.
  Значит Apple Developer Program ($99/год), Xcode, Swift и пересборка каждые 7 дней не нужны.
  Взамен получаем: тот же Python-стек, тот же `scp`-деплой, работу на телефоне и ноуте сразу.
  Отказываемся от виджетов, Siri и надёжного оффлайна — для v1 это не нужно.
- **API-ключ LLM никогда не уходит в браузер.** Вызов модели делает бэкенд; фронтенд знает
  только сессионную куку.
- **Провайдер модели — конфиг, а не архитектура.** Бенчмарки 2026 показывают, что открытая
  Qwen3-VL-8B конкурентна на распознавании блюд (72–76%), но проваливает упакованные продукты
  (44%), а оценку массы в граммах плохо делают *все* модели. Поэтому: абстракция провайдера,
  граммовку подтверждает человек на экране правки, а выбор модели решается замером на своих фото.
- **Модель не считает БЖУ — она их не знает, она их вспоминает.** Это главное решение.
  Задача распадается на два независимых шага: *распознавание* («что на тарелке и сколько грамм»)
  и *расчёт питательности* («сколько в 180 г гречки белка»). Второй шаг — детерминированный
  лукап в справочнике, а не работа для LLM. Справочники бесплатны: **USDA FoodData Central**
  (бесплатный ключ, 1000 req/час, 140+ нутриентов на 100 г, generic-еда) и **Open Food Facts**
  (уже в репозитории, `search_products()` api.py:632, брендовое). Это убирает главный источник
  галлюцинаций и делает текстовый путь практически бесплатным.

## Целевая архитектура

```
Браузер на iPhone / ноуте  ──PWA с экрана «Домой»
  │  session cookie
  ▼
FastAPI на rpi.local  ── GET /  → StaticFiles(webapp/)
  │
  ├─ POST /recognize  ──шаг 1: РАСПОЗНАВАНИЕ (нужна LLM) ───┐
  │    │                   «что за еда + сколько грамм»      ├─ Anthropic API
  │    │                                                      ├─ Gemini API (free tier)
  │    │                                                      └─ Ollama на M4 (локально)
  │    └───────────шаг 2: ПИТАТЕЛЬНОСТЬ (LLM не нужна) ──────┐
  │                        «граммы × справочник = БЖУ»        ├─ Open Food Facts (брендовое)
  │                                                            ├─ USDA FDC     (generic)
  │                                                            └─ overrides.json (RU-специфика)
  ├─ POST /logs     (существует)
  └─ GET  /day      (существует)
```

Apple Health продолжает работать как раньше — Shortcut ходит в `/export/pending` напрямую и
про web-приложение ничего не знает.

`/recognize` **ничего не сохраняет** — возвращает черновик. Сохранение остаётся за существующим
`POST /logs`. Это намеренно: оценка порций — слабое место любой модели, поэтому экран правки
перед записью является частью дизайна, а не костылём.

Следствие разделения: **текстовый путь почти не стоит денег.** На «200 г куриной грудки и гречка»
модель делает только разбор строки в `[(куриная грудка, 200 г), (гречка, ?)]` — это сотни
токенов, посильно даже 3B-модели локально. Все числа приходят из справочников.
Vision нужен исключительно для фото.

## Фаза 0 — линтер, тесты, CI ✅ сделано

Сейчас в репозитории нет ни тестов, ни линтера, ни `pyproject.toml`, ни CI. Ставим это **первым**:
Фаза 1 меняет `_get_db()` (WAL + вынос инициализации схемы в startup) и добавляет ветвления в
разбор питательности — трогать это без страховки не стоит.

### 0.1 Тулинг

Новый `pyproject.toml` в корне — только конфигурация, **без перехода на packaging**:
`requirements.txt` остаётся источником правды для Dockerfile, ничего в деплое не меняется.

- **Ruff** — линтер и форматтер одним бинарником вместо связки black + flake8 + isort.
  Правила: `E,F,W,I,UP,B,SIM`, `line-length = 100`, target `py312`.
- **pytest** + `httpx` (нужен для `TestClient` и уже приезжает в Фазе 1).
- `requirements-dev.txt`: `pytest`, `ruff`, `pytest-asyncio`. В образ не попадает.

### 0.2 Что чинить до включения линтера

Ruff на текущем коде даст правки в `api.py`: неиспользуемые импорты, порядок импортов,
f-string-и. Прогнать `ruff check --fix` + `ruff format` одним коммитом **отдельно** от
логических изменений, чтобы дифф Фазы 1 остался читаемым.

### 0.3 Тесты — что покрываем и почему именно это

Каталог `food_api/tests/`. Фикстура: `monkeypatch.setenv("DB_PATH", tmp_path / "test.db")` +
`TestClient(app)` — схема создаётся сама, изоляция на тест бесплатная.

| `test_day_summary.py` | `_day_summary` (api.py:183–274): суммы по всем 9 нутриентам, группировка по `MEAL_ORDER`, `progress` с `used_percent` и отрицательным `remaining`, `remaining_with_activity = норма + сожжено − съедено` |
| `test_targets.py` | upsert с частичным обновлением (api.py:420–445): задал только `protein_g` — остальные поля не затёрлись |
| `test_activities.py` | дедуп по `external_id` (уникальный индекс api.py:112): повторный `/activities/import` не плодит дубли |

которая роняет тест при попытке реального запроса, — иначе однажды CI начнёт ходить в интернет
и падать по чужой недоступности.

### 0.4 Тесты для нового кода (пишутся вместе с Фазами 1–2)

### 0.5 CI

`.github/workflows/ci.yml` — на push и pull request, Python 3.12:

```
ruff check .  →  ruff format --check .  →  pytest
```

Без матрицы версий и без публикации покрытия: один рантайм, личный проект, лишний шум не нужен.

Локально то же самое одной командой — `Makefile` с целями `lint` / `test` / `check`.
Pre-commit-хук для линтера и тестов не ставим: на личном проекте он чаще мешает, CI поймает.
Для секретов — наоборот, см. §0.7.

### 0.7 Сканирование секретов ✅ сделано

Единственная проверка, которую **нельзя** оставлять только на CI: к моменту, когда джоба
покраснела, ключ уже в истории и его надо отзывать, а не исправлять. Поэтому две линии:

1. **Pre-commit-хук** — `scripts/hooks/pre-commit`, включается `make hooks`
   (`git config core.hooksPath scripts/hooks`, а не копия в `.git/hooks` — так хук
   версионируется вместе с репозиторием). Смотрит только staged-изменения, ~50 мс.
2. **Джоба `secrets` в CI** — та же проверка по всей истории, `fetch-depth: 0`.
   Ловит то, что закоммитили с `--no-verify` или до включения хука.

Обе вызывают один `scripts/check_secrets.sh` (`--staged` / `--history`), чтобы локально
и в CI не разъезжались правила. Скрипт делает две вещи:

- **`.env` под контролем версий** — отдельная проверка по именам файлов, до всякой регулярки.
  `.env.example`/`.sample`/`.template` разрешены.
- **`gitleaks`** (в CI пин `8.28.0`, локально `brew install gitleaks`) с `.gitleaks.toml`:
  дефолтные правила (`useDefault = true`: AWS, GitHub PAT, OpenAI, Google, приватные ключи)
  плюс своё правило на `FOOD_API_KEY`/`USDA_API_KEY`/`ANTHROPIC_API_KEY`/`GEMINI_API_KEY`.

Замеренная тонкость: своё правило сразу дало ложный позитив на `usda_api_key=usda_api_key`
(передача одноимённого аргумента в `nutrition.py`). Go RE2 не умеет lookahead, поэтому
отсекается не регуляркой правила, а `[[rules.allowlists]]` с `regexTarget = "match"`:
значение вида snake_case с подчёркиванием — это имя переменной, настоящий ключ так не выглядит.

Проверено вживую: коммит с `ANTHROPIC_API_KEY = "sk-ant-..."` и коммит с `.env` блокируются,
история репозитория чистая.

### 0.6 Чего НЕ делаем

JS в `webapp/` не линтуем. Любой линтер для фронта тянет npm и `node_modules`, а Фаза 2 прямо
построена на «без сборки, деплой тем же `scp`». Размен осознанный: сотня строк ванильного JS
не окупает тулчейн. Если фронт разрастётся — вернуться к `deno lint` (один бинарник, без
`package.json`).

## Фаза 1 — слой распознавания в бэкенде

### 1.1 `food_api/recognize_prompt.md` (новый)

Извлечь из `gpt_prompt.md` секцию **«Logging food»**. Выбросить «RULE #1 — reply format»,
таблицы прогресса и suggestions — это работа UI. **Секцию «Nutrition sources» выбросить целиком**
— она становится кодом (шаг 2), а не инструкцией модели.

Задача модели сужается до: перечислить съеденное, оценить количество, классифицировать каждую
позицию как `branded` (есть бренд → искать в OFF) или `generic` (искать в USDA), дать
`lookup_query` на английском для USDA. Числа БЖУ модель **не возвращает вообще** — это отрезает
галлюцинацию на уровне схемы ответа.

### 1.2 `food_api/recognize.py` — шаг 1, распознавание

```python
class Recognizer(Protocol):
    def recognize(self, text: str | None, image_b64: str | None) -> RecognizedMeal: ...
```

Схема ответа: `{items: [{name, quantity, unit, kind: branded|generic, lookup_query, brand?}],
meal_type, notes, confidence}`.

- **`AnthropicRecognizer`** — `client.messages.create(...)` с
  `output_config={"format": {"type": "json_schema", "schema": RECOGNIZE_SCHEMA}}`.
  Structured outputs гарантируют форму — парсить текст не нужно.
  `cache_control: {"type": "ephemeral"}` на системном промпте. Модель из env `RECOGNIZE_MODEL`,
  по умолчанию `claude-opus-5`.
- **`GeminiRecognizer`** — бесплатный тариф Google AI Studio, `responseSchema` для structured
  output. Квоты (март 2026): 2.5 Flash — 250 req/день, 5–10 RPM; Flash-Lite — 1000 req/день.
  **Оговорка:** на бесплатном тарифе Google использует данные для обучения. Здесь это фото еды
  и данные о здоровье — осознанный размен, поэтому провайдер не ставится дефолтом.
  Квоты уже резались в декабре 2025 — не строить на них ничего критичного.
- **`LocalRecognizer`** — POST на `LOCAL_LLM_URL` (`/v1/chat/completions`, Ollama на M4).
  Локальные модели схему держат хуже — обязательна валидация через Pydantic + один retry
  с текстом ошибки в промпте.
- Выбор через `RECOGNIZE_PROVIDER=anthropic|gemini|local`, фолбэк на следующий при ошибке.

### 1.3 `food_api/nutrition.py` — шаг 2, питательность (без LLM) ✅ сделано

`resolve(items: list[RecognizedItem]) -> list[FoodItemIn]`, по источнику на каждый вид:

1. **`overrides.json`** — локальная таблица на 30–50 позиций для RU-специфики, которой в USDA
   нет или она названа иначе (сырники, творог 5%, кефир 3.2%, докторская). Проверяется первой,
   правится руками, растёт по мере использования.
2. **`kind == "branded"`** → существующая `search_products()` (api.py:632, Open Food Facts).
   Скейлинг `per_100g` на съеденные граммы через уже написанную `_off_value()` (api.py:625).
3. **`kind == "generic"`** → USDA FoodData Central. Уточнено по живому API:
   `/foods/search` отдаёт **урезанный** список нутриентов (у Foundation-записей там
   нет даже калорий), поэтому по кандидатам дозапрашивается `/food/{fdcId}` и берётся
   первый, у кого калории есть. SR Legacy опрашивается раньше Foundation — панели
   полнее. Энергия приходит дважды: 1008 в kcal и 1062 в kJ, фильтруем по единице.
4. **Единица не переводится в граммы** («2 сырника») → `needs_manual`. Средний вес
   штуки не подставляем: это было бы то же выдумывание числа.
5. **Ничего не нашлось** → вернуть позицию с `needs_manual: true` и пустыми нутриентами. UI подсвечивает её
   красным и требует ручного ввода. Лучше честная дырка, чем выдуманное число.

Результат всегда снабжается `source_ref` (`"USDA 170287"` / `"OFF Ehrmann High Protein"` /
`"override"` / `"manual"`), который показывается в UI — видно, откуда взялась каждая цифра.

**Кэш:** таблица `nutrition_cache(source, query, per_100g_json, source_ref, fetched_at)`
в той же SQLite. Гречка ищется один раз в жизни, лимит USDA (1000 req/час) перестаёт
быть темой.

**Известная слабость (замерено на живом API).** Совпадение по первому результату
посредственное: «гречка» → *Buckwheat flour, whole-groat* (мука вместо крупы),
«куриная грудка» → *breast, meat and skin* (с кожей, 172 против ~110 ккал/100 г).
Числа берутся из справочника корректно — промахивается сопоставление. Смягчено тем,
что `source_ref` виден на экране правки. Кандидат на улучшение: возвращать 2–3
альтернативы и давать выбор в UI (см. §2.4).

### 1.4 Новый эндпоинт в `api.py`

`POST /recognize` (с `dependencies=[Depends(_check_key)]`, рядом с `/logs`):
приём `{text?: str, image_b64?: str, meal_type?: str, consumed_at?: str}` →
`recognize()` → `resolve()` → возврат черновика `FoodLogIn` + `source_ref`/`needs_manual`/`notes`.
Хендлер **`async def`** с `httpx.AsyncClient`, не синхронный `def`: вызов модели долгий (5–20 с),
иначе он занимает воркер из общего пула — ровно та проблема, что `MULTIUSER.md` §1 отмечает
для 15-секундного `/products`. Лукапы в USDA/OFF пускать через `asyncio.gather`.

### 1.5 Обвязка

- `food_api/requirements.txt` += `anthropic>=0.60`, `httpx`, `google-genai` (если берём Gemini).
  Сейчас в проекте только stdlib `urllib.request` — для async-пути он не годится.
- `.env.example` += `RECOGNIZE_PROVIDER`, `RECOGNIZE_MODEL`, `ANTHROPIC_API_KEY`,
  `GEMINI_API_KEY`, `LOCAL_LLM_URL`, `USDA_API_KEY`.
- Ограничение размера `image_b64` (отказ >1.5 МБ) — защита от случайного 12-МП оригинала.

### 1.6 WAL — обязателен, а не желателен ✅ сделано

**Решено: база общая** с работающим food-api из `meow_food`. Один файл `food.db`,
два процесса-писателя, поэтому `PRAGMA journal_mode=WAL` + `busy_timeout=5000`
обязательны (`MULTIUSER.md` §4, пункт 1). Схема создаётся один раз в `lifespan`,
а не на каждом запросе. Общая база означает, что еда из приложения видна Custom GPT
и попадает в ту же очередь Apple Health.

## Фаза 2 — web-приложение (v1: фото/текст → лог + экран дня)

Новый каталог `meow_food/webapp/`. **Без сборки:** ванильный HTML/CSS/JS, ES-модули, никаких
npm, бандлеров и node_modules. Причина прагматичная — деплой остаётся тем же `scp`, что уже
описан в README, и на Pi ничего не собирается.

| Файл | Назначение |
|---|---|
| `index.html` | одна страница, четыре секции-экрана, переключение через `hidden` |
| `app.js` | состояние + рендер; `fetch` с `credentials: 'same-origin'` |
| `api.js` | обёртки `recognize()` / `log()` / `day()` / `login()` |
| `styles.css` | тёмная тема, крупные тап-таргеты, безопасные зоны iOS |
| `manifest.webmanifest` | имя, иконки, `display: standalone` |
| `sw.js` | кэш статики, чтобы оболочка открывалась мгновенно |
| `icons/` | 180×180 apple-touch-icon + 192/512 для манифеста |

Экраны: **Сегодня** (таблица прогресса БЖУ + приёмы пищи), **Добавить** (камера / фото / текст),
**Правка** (редактируемые позиции → сохранение), **Настройки** (ключ, выход).

### 2.1 Отдача статики из FastAPI

```python
app.mount("/app", StaticFiles(directory="webapp", html=True), name="webapp")
```
В Dockerfile добавить `COPY webapp/ /app/webapp/` — сейчас копируется только `api.py`.

### 2.2 Авторизация: кука вместо ключа в JS

Сейчас `_check_key` (api.py:142) читает только заголовок `X-API-Key`. Расширить до
«заголовок **или** кука `session`» — обратная совместимость с Shortcut и garmin-sync сохраняется
полностью. Плюс `POST /auth/login` (принимает `FOOD_API_KEY`, ставит `HttpOnly`, `Secure`,
`SameSite=Lax` куку на год) и `POST /auth/logout`.

Почему не хранить ключ в `localStorage`: Safari чистит script-writable storage при простое,
и ключ будет периодически теряться. Плюс `HttpOnly`-кука недоступна из JS — при XSS её не украсть.

### 2.3 Камера и сжатие

```html
<input type="file" accept="image/*" capture="environment">
```
На iOS открывает камеру сразу. Дальше в JS: `createImageBitmap` → `<canvas>` → long edge 1024 px
→ `toBlob('image/jpeg', 0.7)` (≈150 КБ) → base64. Сжатие **обязательно на клиенте**: держит
изображение около ~1100 токенов и не грузит канал Pi.

### 2.4 Экран правки — центральный, а не подтверждение

Название, граммовка и БЖУ каждой позиции правятся руками; граммы — главное поле, потому что это
слабое место любой модели. Под каждой позицией — `source_ref` («USDA 170287», «OFF: Ehrmann High
Protein»), видно происхождение цифр. Позиции с `needs_manual: true` подсвечены и блокируют
сохранение, пока не заполнены.

### 2.5 Мелочи, которые решают ощущение «это приложение»

- `<meta name="apple-mobile-web-app-capable" content="yes">` + `apple-touch-icon` → запуск с
  экрана «Домой» без адресной строки. На iPhone это WebClip, а не полноценная PWA — service
  worker урезан, Background Sync нет. Для сетевого по своей природе приложения это неважно.
- Таймаут на `/recognize` 60 с + явный индикатор: Pi + туннель + модель дают 5–20 с.
- Оптимистичный UI при сохранении: `POST /logs` возвращает готовый `day` (api.py:353) —
  перерисовываем экран дня прямо из ответа, без второго запроса.
- `progress` / `remaining_with_activity` рендерятся как есть: весь расчёт уже в `_day_summary`
  (api.py:255–273), дублировать на JS нечего.
- Данные живут на сервере, поэтому вычистка браузерного хранилища ничего не ломает.

### 2.6 Доступ снаружи (решить до деплоя)

ngrok на бесплатном тарифе показывает **заглушку перед HTML-трафиком** — API с заголовками её
не видит, а браузер, открывающий страницу, упрётся. Клик «Visit» ставит cookie на 7 дней, так
что жить можно, но для запуска с экрана «Домой» это ломает ощущение приложения.

**Рекомендация: Cloudflare Tunnel** — бесплатно, без заглушки, свой домен, без лимитов трафика.
Это ровно пункт из `MULTIUSER.md` §5 (Phase 2), просто делается раньше. Альтернатива на первое
время — оставить ngrok и мириться с еженедельным тапом.

## Фаза 3 — выбор модели по замеру, а не по ощущениям

`food_api/eval/run_eval.py` + `food_api/eval/photos/` + `ground_truth.json`.

1. Снять ~20 фото типичных для тебя блюд, взвесив порции (это единственный способ получить
   честный ground truth по граммам).
2. Прогнать каждое фото через все настроенные провайдеры.
3. Вывести таблицу: MAE по ккал, MAE по белку, доля верно названных блюд, время ответа,
   стоимость вызова.

Кандидаты: `claude-opus-5`, `claude-sonnet-5`, `claude-haiku-4-5`, `gemini-2.5-flash` (free tier),
локальная `qwen3-vl:8b` через Ollama на M4 (`brew install ollama`, ~6 ГБ в 4-битном кванте).

Важно: после разделения на шаги **eval меряет только шаг 1** — распознала ли модель блюдо и
угадала ли граммовку. БЖУ приходят из справочника и от модели не зависят, поэтому разброс между
провайдерами должен резко сократиться по сравнению с «всё делает LLM». Если так и выйдет —
можно смело брать самый дешёвый или локальный вариант.

Локальный вариант бесплатен, но требует, чтобы Mac был включён и доступен с Pi
(проще всего — Tailscale между ними). Практичная конфигурация: `local` как дефолт,
автоматический фолбэк на Anthropic при недоступности.

   затем `curl -X POST localhost:8000/recognize -H 'X-API-Key: dev' -d '{"text":"200 г куриной грудки и гречка"}'`
   → в ответе позиции с ненулевыми БЖУ.
   Ключевая проверка: у каждой позиции проставлен `source_ref` — цифры пришли из справочника,

2. Фото: то же самое с `image_b64` реального снимка → брендовый продукт подтянулся из

4. Деплой на Pi штатной командой из README (`scp` + `docker compose up -d --build`),
   `curl 127.0.0.1:8010/health` на сервере.
5. Web: открыть `http://localhost:8000/app` в десктопном Safari/Chrome — логин, текстовый ввод,
